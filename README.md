## 二、它是怎么工作的（先讲人话）

把手机弹出的支付通知想象成一张**收银小票**：

1. 知账只看小票的**标题和正文**，看完就用于记账，不进聊天记录、不读通讯录。
2. 三道关卡：**只认白名单里的 App**（微信、支付宝、淘宝、京东、拼多多、美团、抖音）→ **只认「付款 / 收款 / 退款 + 明确金额」** → **同一张小票算一次指纹**，重复弹的通知自动忽略。
3. 账本记在**手机本地**（工程上叫 Room 数据库），没有云同步、没有账号。
4. 分类分两层，这是本应用最关键的设计：
   - **常见商户走本地关键词规则**，当场秒分（像按小票抬头直接丢进对应文件夹）；
   - **认不出来的攒着**，等你在「智能分类」页勾选后，**一批最多 20 笔合并成一次 API 请求**（像月底请会计统一整理一次），**不是每付一笔就联网问一次**。
5. 明确写了商户和金额的算「高置信度」，可直接入账；只写了金额没写商户的算「低置信度」，进待确认等你核对。这个开关可以随时关掉，关掉后**所有**识别结果都要你确认。

术语一句话对照：读通知 = `NotificationListenerService`；去重指纹 = `SHA-256 + 数据库唯一约束`；本地分类 = 关键词规则表；批量分类 = 一次 `chat/completions` 请求。

## 四、第一次打开必须做的事

1. **开通知使用权**：系统设置 → 通知使用权 / 特殊应用权限 → 通知访问 → 勾选「知账」。这是安卓的规定，普通 App 不能自己给自己开。**这是最稳妥、最推荐的方式。**
2. 首页顶部出现「自动记账运行中」才算真的生效。
3. **小米 / 红米 / 部分国产 ROM 还要注意**：给知账开「自启动」、「后台运行无限制」、省电策略设为「无限制」。否则系统会在后台杀掉监听服务，通知就抓不到了。
4. 建议初期在「我的」页**关掉「高置信度自动入账」**，先观察一两天识别准不准，再决定要不要放开。

## 五、无 Root 的 ADB 授权（可选，不是必须）

**原理**：安卓不允许普通 App 自己打开「读通知」这个敏感开关，但允许电脑通过官方调试通道替你打开。这是系统自带的调试能力，**不是破解、不需要 Root、不解锁 Bootloader**。

`cmd notification` 是 Android 13 起系统提供的官方命令，效果最接近在系统设置里手动勾选：

```
adb shell cmd notification allow_listener site.zhizhang.app.debug/site.zhizhang.app.service.PaymentNotificationListener
```

旧系统（Android 12 及以下）用兼容写法，执行后**回到 App「我的」页点一下顶部按钮**：

```
adb shell pm grant site.zhizhang.app.debug android.permission.WRITE_SECURE_SETTINGS
```

**Windows 用户**：双击 `grant-notification-access.bat` 即可，脚本会自动尝试上面两条命令，并把 App 拉起来。前提是手机已开启「开发者选项 → USB 调试」并授权了这台电脑。

**这里的坑，务必看：**

- Android 14 及以上对「绕过设置界面」加进来的监听器可能标记为**受限**：App 显示已授权却仍抓不到通知。此时请老老实实去系统设置里手动开一次，这是唯一可靠解。
- 少数国产 ROM 不支持 `cmd notification`，脚本会静默失败，用第二条 `pm grant` 兜底，或直接用系统设置。
- USB 调试用完建议关掉；这条命令只放开「通知使用权」这一项，不授予 Root、不读取支付密码、短信或账户凭据。

## 六、日常怎么用

| 页面 | 能做什么 |
| --- | --- |
| 首页 | 本月总支出 / 收入、已确认笔数、最近流水；点流水可改分类、改备注、删除 |
| 自动 | 权限状态、高置信度开关、**待确认流水**（确认入账 / 忽略）、**粘贴通知文本测试** |
| 分类 | 本地规则统计、勾选未分类流水、点一次「批量分类」；配置 API 地址 / 模型 / 密钥 |
| 流水 | 搜索商户 / 分类 / 金额，按全部 / 支出 / 收入 / 待确认筛选，导出 CSV |
| 我的 | 权限、ADB 说明、API 配置、隐私开关、导出账本 |

**不实际付款也能验证识别**：进入「自动 → 粘贴通知文本测试」，默认已填好一条微信支付样例，点「解析并加入待确认」即可看到完整链路。也可以把真实通知文字粘进去试。

**桌面小组件**：长按安卓桌面 → 小组件 → 知账 → 添加「本月支出」，点小组件可返回账本。数据由账本变更时主动刷新。

**API 配置**：留空即完全离线。填写时填兼容 OpenAI `chat/completions` 的 Base URL（如 `https://.../v1`）、模型名和密钥。密钥用 Android Keystore 的 AES-GCM 加密保存；默认**只发送商户名和收支类型，金额不发**，可在设置里打开。

## 八、已知限制（请如实看待，不要当成「万能自动记账」）

1. **通知格式会变**：各家 App 版本、各家手机 ROM 的折叠 / 精简通知写法都不同，解析器是按常见格式写的规则，**不保证覆盖所有版本**。
2. **没有金额就不猜**：像「订单支付成功」但通知里没有金额、没有商户的通知，当前实现会**直接跳过**，不会编一个金额出来 —— 这类必须手动补录（右下角「＋」）。
3. **抓不到的场景**：通知被关闭 / 静默 / 折叠、锁屏不显示内容、App 在后台被系统杀掉、付款后根本不发通知、银行 App 或信用卡消费。
4. **自动入账可能误判**：转账、红包、理财、充值等字样可能与支付混淆。初期建议关闭自动入账，用待确认兜底。
5. **功能边界**：暂无云同步、多设备、预算提醒、账单导入、周期统计图表、多账本；收入与退款能识别为收入，但没有做完整的账户余额对账。
6. **验证范围**：单元测试 9 项通过；界面与完整链路在 **Android 模拟器（API 36.1）** 上实测通过，**尚未在小米等真机上做多机型适配**。国产 ROM 的通知权限和后台保活差异需要真机再调。
7. **AI 分类不含密钥**，需要你自己配置接口；不配置时所有分类都在本机完成。

## 十一、附：MuMu 开屏广告已禁用

**它是什么**：MuMu 启动时的开屏广告像影院的「贴片广告」。本机有一张广告排期表 `imageManager.json`，里面原本存着 2 条在投的游戏推广；每次启动还会联网从 `api.mumu.nie.netease.com/api/v2/campaign/launcher/launching` 拉新的，写回这张表。

**做了什么**（可逆，没删任何文件、没改系统 hosts、不需要管理员或 Root）：

1. 把排期表备份为 `imageManager.json.zhizhang-bak`；
2. 把表内容改成空清单 `{"info":[]}`，等于给它一张空白排期表；
3. 把文件设为**只读**，联网拉到的新广告也写不回来（相当于把笔拿走）。

文件位置：`%APPDATA%\Netease\MuMuPlayer\data\startupImage\imageManager.json`

**验证结果**：重启 MuMu 两次后，日志里 `need show`、广告展示事件、联网拉取解析**全部为 0**，只剩「初始化开屏组件」这一行；知账仍正常启动，账本数据 ¥35.50 / 1 笔 完整保留。

**一键脚本**：`mumu-splash-ad.bat`

| 操作 | 怎么做 |
| --- | --- |
| 禁用 | 双击（MuMu 更新后重跑一次即可） |
| 恢复原样 | 命令行执行 `mumu-splash-ad.bat restore` |
| 脚本调用不弹窗 | 第二个参数加 `/quiet`，例如 `mumu-splash-ad.bat disable /quiet` |

**两个坑**：

- **MuMu 版本更新会重置**：更新可能重建这个目录或覆盖排期表，广告会回来，重跑一次脚本即可。所以没去改 `MuMuNxUpdater.exe`，保持模拟器可正常更新。
- **如果还有别的广告**：这轮只处理「开屏广告」。消息中心推送、模拟器桌面的游戏推荐、游戏中心 App 属于另外几类，需要另外处理（例如更换安卓桌面、冻结 `com.mumu.store`）。想彻底断网拉广告可屏蔽 `api.mumu.nie.netease.com`，但改 hosts 需要管理员权限、还可能影响 MuMu 的更新与账号服务，**本轮没有动**，需要的话再单独做。

新增一个 App 的最短路径：在 `SupportedApps.kt` 加包名 → 往 `PaymentParser.kt` 补该 App 的通知句式 → 在 `app/src/test/.../PaymentParserTest.kt` 加一条真实通知样例的测试 → 重新构建。

## 十二、小米真机（HyperOS / Android 16）通知使用权修复

**先讲人话**：小米把「让 App 读通知」这个开关上了三道锁，像小区门禁——第一道是 USB 线没被信任，第二道是「外来安装的 App 不给开特殊权限」（开关直接变灰，这就是手动怎么点都没用的原因），第三道是就算登记了名字，保安也没真的把门打开（服务没绑定）。ADB 做的事就是分别刷开这三道锁，**全程不需要 Root**。

### 本机实测环境

| 项 | 值 |
| --- | --- |
| 机型 / 系统 | Xiaomi `2211133C`，HyperOS `V816` / `OS3.0.309.0.WMCCNXM` |
| Android | 16（API 36） |
| 设备序列号 | 由 `adb devices` 自动获取，辅助脚本不再写死本机设备信息 |
| 已装支付 App | 微信、支付宝、淘宝、京东、拼多多、美团、抖音（白名单齐全） |

### 根因与对应解法

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| `adb devices` 显示 `unauthorized` | 手机没确认「允许 USB 调试」 | 手机弹窗勾选「一律允许这台计算机」再点确定（**这步只能手动**） |
| 系统设置里开关灰色／点了没反应 | 侧载应用被 HyperOS 标记 `ACCESS_RESTRICTED_SETTINGS=ignore` | `appops set <包名> ACCESS_RESTRICTED_SETTINGS allow` |
| 允许列表里有名字，但收不到通知 | `allow_listener` 只写了标记，系统没执行 `bindService` | **`disallow_listener` → `allow_listener` 重新触发绑定**（实测关键步） |
| 后台被杀、重启后失效 | 小米省电策略 | `cmd deviceidle whitelist +<包名>`；并在手机里手动开自启动 |

### 修复脚本

`fix-xiaomi-notification.bat`（双击即可，内含等待 USB 授权，最多 8 分钟），实际逻辑在 `fix-xiaomi-notification.py`：

| 用法 | 命令 |
| --- | --- |
| 完整修复（推荐） | 双击 `fix-xiaomi-notification.bat` |
| 已授权，直接跑 | `python fix-xiaomi-notification.py --no-wait` |
| 只诊断不改设置 | `python fix-xiaomi-notification.py --check` |

脚本依次做：① 解除受限设置 → ② `cmd notification allow_listener` → ③ 兜底 `pm grant WRITE_SECURE_SETTINGS` → ④ 电池白名单 → ⑤ **撤权再授权强制绑定** → ⑥ 启动 App 并验证。

### 判定是否真的解决（三条都要满足）

1. 系统设置 → 通知使用权：**「知账」出现在「已允许」分组**
2. `adb shell dumpsys notification --noredact` 的 **Live notification listeners** 里有 `PaymentNotificationListener`
3. App 首页显示 **「自动记账运行中」**

只有第 1 条不算解决——那只是登记了名字，服务没连上照样收不到通知。这是本轮最容易踩的坑。

### 实测结果

- 修复前：`enabled_notification_listeners` 只有小米弹幕服务；`ACCESS_RESTRICTED_SETTINGS: ignore`
- 修复后：允许列表含知账；`appops` 变 `allow`；**Live listeners 从 12 变 13 并出现知账服务**；系统设置页「已允许」有知账；首页显示「自动记账运行中」
- 电池白名单已加入 `user,site.zhizhang.app.debug,10369`

### 仍需你手动做的两件事

1. **自启动**：手机管家 → 应用管理 → 知账 → 允许自启动；最近任务里把知账卡片下拉加锁。这是小米私有开关，ADB 改不了。
2. **真实支付验证**：ADB 注入的通知包名是 `com.android.shell`，不在支付白名单内，会被解析器按设计忽略，所以**不能用它伪造支付通知**。请用微信/支付宝真实付一笔小额，看是否自动进入待确认；不实际付款也能用「自动」页的「粘贴通知文本测试」验证解析规则。

### 已知边界

- 小米若需 `pm grant WRITE_SECURE_SETTINGS` 生效，要先在开发者选项打开 **「USB 调试（安全设置）」**（需登录小米账号）；本方案主要依赖 `cmd notification` 系统命令，不强依赖这一项。
- 系统大版本更新可能重置特殊权限，届时重跑一次脚本即可。
- 手机锁屏/息屏后 `adb shell input` 会报 `INJECT_EVENTS` 权限错误，界面自动化测试需要先解锁亮屏；但权限状态检查不受影响。

## 十三、真机验证操作清单（照着做即可）

### 先看一眼状态

打开知账首页，顶部应显示 **「自动记账运行中」**。如果不是，先双击 `fix-xiaomi-notification.bat`。

### 建议先改一个开关

「我的」→ 关掉 **「高置信度自动入账」**。这样所有识别到的流水都会进「待确认」等你核对，初期更容易看清抓到了什么，也避免误判直接记进账本。

### 路径 A：不花钱，先验证解析规则

1. 底部点「自动」→ 往下滚 → 点 **「粘贴通知文本测试」**
2. 里面已预填一条微信支付样例，直接点 **「解析并加入待确认」**
3. 回到待确认列表，应看到「肯德基（科技园店）¥35.50 · 餐饮美食」
4. 点 **「确认入账」** → 回首页，总支出应变成 ¥35.50

### 路径 B：真实小额支付，验证完整自动记账

1. 付款**前**双击 `verify-xiaomi-ledger.bat`（保存基线，此时账本应为 0 笔或你已有的笔数）
2. 用微信或支付宝真实付一笔小额（例如便利店扫码）
3. 等 3–5 秒，双击 `verify-xiaomi-ledger.bat diff`
4. **判定标准**：出现「✅ 新增 N 笔流水」，且「原始通知」一栏有内容 → 说明确实是通知监听抓到的，不是手动记的

> `verify-xiaomi-ledger.bat` 是只读的，不改手机任何设置。它直接读真机账本数据库，所以能给出比截图更硬的证据。

### 没抓到时按这个顺序自检

| 检查 | 怎么办 |
| --- | --- |
| 通知里有明确金额和商户吗？ | 只有「订单支付成功」而无金额的通知，解析器按设计跳过，需手动补录 |
| 通知被折叠/静默了吗？ | 下拉通知栏展开，或到系统设置里允许该 App 的锁屏/横幅通知 |
| 「高置信度自动入账」是开着的吗？ | 开着时流水会直接进「已入账」，不在待确认列表，去「流水」页看 |
| 后台被杀了吗？ | 确认自启动已开、最近任务里知账已加锁、电池无限制 |
| 权限还在吗？ | 跑 `python fix-xiaomi-notification.py --check`，看结论是否为「权限已完全生效」 |

### 为什么界面点击不能由电脑代劳

小米禁止 ADB 注入点击事件（`INJECT_EVENTS` 被系统拒绝），所以 **App 里的按钮只能你在手机上亲手点**。电脑端能做的是：查权限、读账本、验收结果、修复系统级开关——这些都不需要模拟点击。

## 十四、真机实测反馈：转账与电商支付没自动入账（重要）

用户实测「微信给朋友转账」+「拼多多购物」两笔，**账本都没有新增流水**（账本里只有「粘贴通知测试」产生的样例 ¥35.50）。

### 排查结论：不是权限问题

| 证据 | 结果 |
| --- | --- |
| 允许列表 / 监听服务绑定 | 都在 ✅ |
| 注入一条交易类测试通知 | **被监听服务收到并记录** ✅ |
| 系统通知记录里的微信通知 | 正文是「微信支付：『支付分先用后付』订单已取消」——这是取消通知，按设计应忽略 |

也就是说「门铃」是通的，但那两笔**没有产生一条能被识别成支付的系统通知**。三类常见原因：

1. **微信转账给朋友**属于聊天里的转账消息（`category=msg` 消息通道），不是「微信支付凭证」推送；微信往往只给一条聊天通知，甚至不弹系统通知。
2. **拼多多购物**的扣款通知通常由**微信支付/支付宝**发出（因为用它们付款），而不是拼多多 App 自身；电商 App 自己发的常是「订单支付成功 / 待发货」且**没有金额**，解析器按设计跳过，不猜金额。
3. 通知被小米折叠成一组、锁屏时 `vis=PRIVATE` 隐藏正文，或由 MiPush 代发导致包名不在白名单。

> 小米还禁用了系统通知历史（`settings put secure notification_history_enabled 1` 返回 null），也拒绝 `cmd notification redact_otp_from_untrusted_listeners`（需要 `WRITE_SECURE_SETTINGS`），所以**过去那几条的原文无法回溯**，只能靠下一笔实时抓。

### 本轮代码改进（版本仍为 1.01）

- **解析规则补全**：新增「转账成功 / 已转账 / 转出 / 转账给 / 订单支付成功 / 支付完成 / 交易成功」等句式，金额提取加「转账 / 合计 / 订单金额」，商户提取加「转账给 X」「在 X 消费」。
- **过滤词校正**：加「订单已取消 / 交易关闭」；**刻意不放**「待发货 / 待收货」，因为电商支付成功通知常附带这些状态词，放进去会误杀真实流水。
- **单元测试 9 → 13 项**，新增转账、拼多多订单、带发货状态词、取消订单四个用例，全部通过。
- **新增通知诊断日志** `util/NotificationLog.kt`：只记录含支付/订单/金额字样的通知，明文仅存 App 私有目录、不上传；记录包名、标题、正文、是否解析、未入账原因。
- 「自动」页新增 **「通知诊断 → 查看最近收到的通知」**，手机上就能看到收到了什么、为什么没入账，还能清空记录。
- 监听服务改为「先解析后记录」，所以**通知到了但没入账**也能被看见，不再是无声丢弃。

## 十六、真机抓到第一条真实支付通知：「已扣费¥5.98」为什么没读

用户支付后通知栏明确有通知，但账本没记录。这次**有完整证据链**，不是猜测。

### 证据：通知确实送到 App 了

诊断日志原文（`show-xiaomi-notifications.bat` 可直接看到）：

```json
{"pkg":"com.tencent.mm","title":"微信支付","text":"[2条]微信支付: 已扣费¥5.98",
 "inWhitelist":true,"parsed":false,"reason":"文案未匹配支付规则或缺少金额"}
```

系统通知记录里也确认：`pkg=com.tencent.mm`、`channel=message_channel_new_id`、`category=msg`、`vis=PRIVATE`，正文完整无脱敏。**权限、绑定、脱敏都不是问题**——是解析器自己的规则没覆盖。

### 两个真实 bug（都已修）

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | `expenseWords` 里有「扣款/已扣款」，但**没有「已扣费/扣费」** | 整条通知被判定「不是支付」直接丢弃 |
| 2 | 微信把多条消息折叠成一条通知时加了 `[2条]` 前缀，金额正则**跨行匹配把它当成 2 元** | 即使补了「已扣费」，也会错记成 ¥2.00 而不是 ¥5.98 |

第 2 个是加单元测试时才暴露的：断言期望 598 分，实际得到 200 分。修法：

- 把「已扣费 / 扣费 / 扣费成功 / 自动扣费 / 免密支付」补进 `expenseWords`
- 解析前先剥掉 `[\d+条]` 折叠计数
- 金额提取改为**带 ¥/￥ 的模式优先**，关键词模式禁止跨行（`[^0-9¥￥\n]`）兜底

### 验证结果

- 单元测试 13 → **16 项，全部通过**（新增真实原文、自动扣费、无金额转账回执三个用例）
- 用真实原文 `[2条]微信支付:已扣费¥5.98` 在真机重放：诊断日志 `parsed=true, amountCents=598`，账本出现 **¥5.98 待确认**
- 修复版 APK 已安装到真机，监听服务重新绑定，`READY=True`

### 一个必须说清的限制

**App 只在通知到达的那一刻解析，不会回溯处理已错过的通知**。所以你原来那条 ¥5.98 本身不会被自动补记；账本里现在这笔是用同样原文重放验证时产生的。下一笔真实支付就会自动进待确认了。

另外这条通知是**微信把多条消息折叠成的摘要**，只有金额、没有商户名，所以分类是「未分类」、标记需要 AI。这属于信息缺失，不是识别错误——要么你在待确认时手动补分类，要么展开通知后把完整原文发我，我再补商户提取规则。

### 实测结果（真机，19:17–19:21）

| 模拟通知 | 结果 |
| --- | --- |
| 微信商户消费 `支付成功,金额12.50元,商户:楼下便利店` | ✅ ¥12.50 · 楼下便利店 · 居家生活 |

### 安全边界（重要）

- 调试旁路用 `BuildConfig.DEBUG &&` 限定，**只在 Debug 构建存在，正式发布包恒为 false**。
- 只接受 `com.android.shell` 且 tag 以 `ZhizhangSim` 开头的通知，或设置页手动打开的开关（默认关闭）；普通 App 伪造不了 `com.android.shell` 包名。
- 设置页「我的 → 调试：模拟支付通知」有开关，验证完可关掉。
- 调试注入固定进入**待确认**，不会直接计入统计。

### 两个踩过的坑（写进脚本注释了）

1. **通知文本不要带 ASCII 空格**：`adb shell cmd notification post` 会把空格后的内容拆成新参数，金额会丢失（实测 `支付成功 金额 12.50 元` 只剩 `支付成功`）。用逗号代替空格。
2. **小米会限流短时间内连续注入的通知**：通知在系统里可见，但监听器不再回调。表现为诊断日志不增长。解法是每条间隔 12 秒；若仍不生效，执行 `cmd notification disallow_listener` → 等 3 秒 → `allow_listener` 重新绑定即可恢复（实测有效）。
3. 升级安装 APK 后监听服务绑定会掉，**必须重新执行上面的 disallow→allow**。

### 产品判断（已实测确认）

「转账给朋友 ¥66.00」被识别成商户「张三」、分类「未分类」、需要 AI。它本质是**资金往来而非消费**，直接算进「本月总支出」会虚高。建议后续把转账单独成一类，或让用户在待确认时决定是否计入支出。这点需要产品定调，本轮未改。

## 十七、拔掉 USB 数据线后，还能自动记账吗？

**能。** 电脑只做过一件事：帮忙把「通知使用权」这个灰色开关打开。开关一旦打开，就是手机自己的设置了，之后有没有电脑完全不影响自动识别。

### 先把关系讲清楚

干活的不是电脑，也不是 ADB。真正收通知的是 Android 系统里一个常驻的**通知监听服务**：微信/支付宝弹通知时，是**手机系统主动推给知账**，不是电脑读给知账。ADB 从头到尾只当过一次「遥控器」，用来绕过小米对侧载应用的限制；授权结果写进了手机自己的磁盘：

| 授权项 | 存在哪里 | 断电/拔线后 |
| --- | --- | --- |
| 通知使用权登记 | `/data/system/users/0/settings_secure.xml` | 仍在 |
| 侧载「受限设置」解除 | appops 持久状态 | 仍在 |
| 电池优化白名单 | `/data/system/deviceidle.xml` | 仍在 |
| 实时绑定的监听服务 | 系统 NotificationManagerService | 仍在（实测 `Live listeners` 有知账） |

顺带一提，USB 调试的 RSA 信任密钥也存在手机里，重新插线**不用再点「允许 USB 调试」**（实测 `kill-server` → 重连后设备直接是 `device`，不是 `unauthorized`）。

AI 批量分类走的是手机自己的网络请求，同样不依赖电脑。

### 本轮实测证据

用 `test-offline-capture.bat` 一键验证（约 30 秒，不花钱、不用二维码）：

1. 电脑预约一条「手机本地 shell 在 20 秒后自己发出」的支付通知；
2. 立刻 `adb kill-server`，**电脑端 ADB 完全断开**；
3. 断开期间通知由手机自己发出；
4. 电脑重新连上后读诊断日志与账本验收。

实测输出：

```
基线：账本 7 笔 / 诊断日志 13 条
>>> 电脑端 ADB 已断开，接下来 26 秒电脑不参与 <<<
诊断日志：pkg=com.android.shell  parsed=True  amount=888
账本流水：¥8.88  拔线自检195356  未分类  PENDING
账本 7 → 8 笔
[PASS] 电脑端 ADB 完全断开期间，手机自己发出的支付通知仍被自动监听到、解析成功并进入待确认
```

更早的一条更贴近真实场景：用户自己付款产生的「微信支付：已扣费¥5.98」，通知由微信发出、App 收到并记进诊断日志，电脑只是事后用来查日志。

> 说明：脚本严格模拟的是「电脑端 ADB 断开」；物理拔线只是额外断掉手机侧 adbd，而通知监听链路与 adbd 无关。要 100% 实证，拔线后正常用手机，等下一笔真实支付看是否自动进待确认即可。脚本会产生一笔 ¥8.88 测试流水，可在「自动」页忽略或删除。

### 什么时候才会真的失效

| 情况 | 表现 | 怎么办 |
| --- | --- | --- |
| 手机重启 / HyperOS 系统更新 | 授权被重置，首页显示「自动记账尚未授权」 | 插上线双击 `fix-xiaomi-notification.bat`；**或纯手机手动开**：设置 → 通知与控制 → 通知使用权（灰色开关已解除，现在能直接勾） |
| 在设置里手动关了知账的通知使用权 | 同上 | 重新勾一次，不需要电脑 |
| 手机管家把 App 冻结 / 强行停止 | 有通知但不入账 | 允许自启动 + 电池无限制 + 最近任务加锁；点开一次知账 |
| 手动在系统设置里「强行停止」App | 监听服务解绑 | 重新打开知账；必要时重跑修复脚本 |
| 连续升级安装 APK | 监听绑定会掉 | 脚本已包含 `disallow_listener` → `allow_listener` 重新绑定 |

排查顺序不变：先双击 `show-xiaomi-notifications.bat` 看诊断日志——分得清「通知根本没送到」还是「送到了但没解析」，再看权限，不用从头猜。

## 十八、只有金额没有商品：自动记账的真实边界（重要产品结论）

用户实测反馈：「微信支付扣了 ¥5.98（在拼多多买东西），但只记到一个数字，没有分类、没有物品、没有信息，等于没记。」

**这个判断是对的，而且情况比预想的更彻底。**

### 先讲清原理：银行流水 ≠ 购物小票

微信/支付宝是**支付通道**，它只知道「钱从哪来、到哪去、多少、几点」，不知道你买了什么。商品明细存在拼多多的**订单系统**里，是另一套数据。

去银行打对账单，上面也只有「某某商户 ¥5.98」；想知道买了什么，得看商场小票。通知监听拿到的就是那张「对账单」，不是「小票」。**这是数据源缺失，不是解析算法不够聪明**——换个正则、换个 AI 也变不出商品名。

小米钱包/同类 App 能显示商户名，靠的是支付凭证里带了商户字段、或接入了账单导入；**它们同样不会凭空读出「买了几提抽纸」**。

### 本轮实测证据（`show-xiaomi-notifications.bat` 可读）

| 事实 | 证据 |
| --- | --- |
| 微信支付凭证只有金额 | `pkg=com.tencent.mm, title=微信支付, text=[2条]微信支付: 已扣费¥5.98`，`dumpsys` 完整 extras 里也只有 title/text，没有商户、商品、订单号 |
| 拼多多**一条交易通知都没发** | App 诊断日志 14 条记录里，没有一条 `pkg=com.xunmeng.pinduoduo`；日志过滤词含「支付/订单/金额」，真发了会被记下 |
| 所以「把电商通知和支付凭证关联」这条路目前没有数据源 | 不是没写关联逻辑，是另一侧根本没推送 |

自动通知能稳定拿到的硬事实只有三项：**金额、时间、支付渠道**。它的价值是「不漏记、金额准」；而「这钱花在哪、买了什么」属于可回顾性，必须靠补录或另一份数据源。

### 本轮已改：不伪装成完整的账，把补录成本降到一次点击

1. 新增 `core/EntryCompleteness.kt`：判定一条流水是否「缺商户 / 缺分类 / 缺买了什么」。渠道名（微信支付、支付宝）和「XX订单」占位名都算信息不足。

### 要真正拿到商品信息，只有这三条合法路径（都不需要 Root）

| --- | --- | --- |
| **A. 账单导入**（信息最全） | 微信/支付宝账单 CSV 里有「交易对方」「商品说明」，按金额+时间与通知流水匹配即可自动补全 | 需要用户定期导出账单文件；是唯一能合法拿到商品名的路径 |

## 十九、手动退出 App 后，后台还能自动记账吗？

**分情况，答案不一样。** 关键先分清一件事：真正收通知的不是 App 界面，而是 **Android 系统绑定的通知监听服务**。

打个比方：App 界面像前台的灯，监听服务像值班室里一直插着电的对讲机。你把前台灯关了（按返回键 / 回桌面 / 锁屏），对讲机照常响；但把整栋楼的电闸拉了（强行停止 / 系统冻结），对讲机就断电，得重新合闸。工程上叫 `NotificationListenerService`，它由系统在有通知时主动推给 App，不需要 App 自己常驻前台、也不需要电脑。

### 四种「退出」的结果

| 你做的动作 | 能不能继续记 | 说明 |
| --- | --- | --- |
| 按返回键 / 回桌面 / 锁屏 | **能，照常** | 实测实时监听列表仍有知账、进程 PID 不变 |
| 从最近任务划掉卡片 | 标准 Android 上系统会重新绑定；小米取决于清理策略 | 建议给知账卡片下拉加锁 |
| 设置里「强行停止」/ 手机管家一键清理 | **不可靠** | 这台小米实测 2 秒内系统就把服务重新拉起（新进程、Live listeners 仍在），但通知回调明显延迟；AOSP 标准语义是必须重新点开 App 才恢复 |
| 重启手机 | 开机后系统自动重绑 | `BootReceiver` 只负责刷新小组件；保险起见开机后点开一次知账 |

### 本轮真机实测（20:16–20:22）

- 回桌面后：`Live listeners` 仍有 `PaymentNotificationListener`，PID `19253` 不变。
- `am force-stop` 后 +2 秒：`live=True`、新 PID `23130`、`stopped=false` —— 小米自动重绑了服务。
- 注入的 ¥6.66 / ¥7.77 两条通知**当时读日志是 16→16，后来日志里出现了**（16→18）：回调延迟了几十秒。
- 另外两条 ¥1.11 / ¥2.22 通知在系统里能看到，但监听器一直没回调 —— 小米对短时间连续注入有限流。

> **重要经验：在这台小米上「没立刻出现」不等于「没记录」。** 排查时先看诊断日志和系统通知列表，别急着下结论说后台死了。

### 新增：把「后台还活着吗」变成界面上看得见的事实

以前首页只显示「自动记账运行中」，那只是**权限登记状态**，不能证明服务真的在收通知。现在首页状态卡显示：

```
自动记账运行中
退出界面仍在后台 · 上次收到通知 20:27
```

实现链路：

1. `SettingsStore.lastNotificationAt` —— 监听服务**每收到一条系统通知**就写一次时间戳（在过滤白名单之前，所以能反映服务是否存活，不代表记了一笔账）；
2. `PaymentNotificationListener.onNotificationPosted()` 开头写入；
3. `MainActivity.onResume()` → `MainViewModel.refreshPermission()` 重读，所以退出期间后台收到的通知，回来打开就能看到；
4. `core/ActivityStatus.kt` 生成文案（同一天显示 `HH:mm`，隔天显示 `MM月dd日 HH:mm`），纯函数，有 4 项单元测试。

真机验证：`shared_prefs/settings.xml` 出现 `<long name="last_notification_at" …/>`；`uiautomator dump` 读到 `退出界面仍在后台 · 上次收到通知 20:27`；截图确认无重叠、无截断。

### 顺手修的布局细节

四个滚动页（首页 / 自动 / 分类 / 我的）统一加了 `FabSafeBottomPadding = PaddingValues(bottom = 88.dp)`，滚到底部时最后一条不会被右下角「＋记一笔」完全盖住。FAB 悬浮时中间行短暂经过其下方是 Material 的常规行为，未改动整体设计。

### 想让后台最稳，请在手机上做这四件事

1. 自启动：已开启 ✅
2. 手机管家 → 省电与电池 → 知账 → **无限制**
3. 最近任务里把知账卡片**下拉加锁**
4. 别用「一键清理」、别在设置里点「强行停止」、别让系统把 App 判为休眠/冻结

单元测试 21 → **25 项全过**；1.01 最终版已装真机，权限 `READY=True`，账本 11 笔保留。

## 二十、「除非卸载，否则一直监视」——能不能做到？

**准确答案：没有实现，而且在不 Root 的前提下，Android 不允许任何第三方 App 做出这个承诺。**

原因不是代码写得不够，是平台规则：手机系统永远有权停掉一个普通应用 —— 用户点「强行停止」、手机管家一键清理/冻结、省电策略、系统更新后重置权限、开机后重新分配资源、卸载。这就像租客不能要求房东「永远不许断水电」。想真正 100% 常驻，只能是系统级应用 / 设备管理器 / Root，都超出了本项目约束。

### 改动前的真实缺口（两个硬事实）

| 缺口 | 证据 |
| --- | --- |
| 开机 / 应用升级后**没有主动恢复** | `BootReceiver` 原来只刷新桌面小组件，不碰监听服务 |
| App **拿不到 `WRITE_SECURE_SETTINGS`** | `dumpsys package` 里该权限只在 `requested permissions`，`install permissions` 中没有 `granted=true`（小米要求另开「USB 调试(安全设置)」）。所以权限一旦被系统清掉，`enableListenerAfterAdbGrant()` 会直接返回 false，App 无法自己重新登记 |

也就是说：**授权被系统整个撤销时，必须用户手动在系统设置里勾一次，或插线重跑 `fix-xiaomi-notification.bat`**。

### 本轮补上的自愈（不 Root、官方 API）

用 `NotificationListenerService.requestRebind()`（API 24+，不需要额外权限）在四个时机主动请系统重新绑定监听服务：

| 触发点 | 实现 |
| --- | --- |
| 开机 `BOOT_COMPLETED` / 应用升级 `MY_PACKAGE_REPLACED` | `BootReceiver` → `ListenerGuard.ensureIfStale()` |
| 用户重新打开 App | `MainActivity.onResume()` → 若 30 分钟没收到任何通知则重绑 |
| 设置页手动点「自检并重新绑定」 | `SettingsScreen` → `ListenerGuard.ensureNow()`，能写安全设置时先补登记 |
| 电脑端验证（仅 Debug） | `am start -S -n <包名>/.MainActivity --ez forceRebind true` |

配套：
- `core/ListenerHealth.kt`：纯函数判断「是否 30 分钟没动静」，4 项单元测试；
- `SettingsStore.lastRebindAt`：记录每次自愈，便于排查；
- **修了一个旧 bug**：`DebugCommandReceiver` 的 uid 检查原来只放行 `2000/0`，但广播由 system_server 分发时读到的是 `1000`，导致 ADB 广播长期静默失效。现放行 `1000/2000/0`，第三方 App 的 uid 仍会被拒。

### 真机验证结果

```
am start -S -n site.zhizhang.app.debug/.MainActivity --ez forceRebind true
→ settings.xml 出现 <long name="last_rebind_at" value="1793796275437" />
→ logcat: I ZhizhangGuard: requestRebind sent
→ Live notification listeners 仍有 PaymentNotificationListener（1 条）
→ enabled_notification_listeners 仍含知账组件
```

> 验证途中踩的坑：小米会**静默丢弃静态广播**（`am broadcast` 返回成功但接收器不执行）；`am start` 复用前台实例时不会走 `onResume`；直接改写 App 私有 `settings.xml` 也被系统拒绝。最后改用 `am start -S` 强制重建 Activity 才拿到确凿证据。

单元测试 25 → **29 项全过**；自愈版 1.01 已装真机，`READY=True`，账本 11 笔保留。

### 仍然做不到的事（请如实看待）

| 场景 | 自愈能救吗 | 用户要做什么 |
| --- | --- | --- |
| 权限登记还在、服务只是解绑（进程被回收、升级、开机） | **能** | 无需操作，四个触发点会自动重绑 |
| 系统把「通知使用权」整个撤销（HyperOS 更新、权限重置、手动关闭） | **不能** | 系统设置里手动勾一次，或插线跑修复脚本 |
| 用户点「强行停止」/ 管家一键清理 / 系统冻结 | **不能** | 重新打开一次知账；别做这些操作 |
| 长时间省电冻结、开机后系统未恢复授权 | 部分 | 电池设「无限制」、允许自启动、最近任务加锁 |
| 卸载 | — | 当然停止 |

### 想更接近「一直监视」，还有两个可选项（本轮未做，等定调）

1. **前台服务 + 常驻通知**：不 Root 下最接近「一直活着」的合法手段，但通知栏会多一条常驻提示，属于明显的产品取舍。
2. **让 App 拿到 `WRITE_SECURE_SETTINGS`**：在手机开发者选项里额外打开「USB 调试(安全设置)」后重跑授权脚本。这样权限被系统重置时，App 有机会自己把组件写回 `enabled_notification_listeners`（Android 14+ 仍可能限制）。

**产品判断**：与其承诺一个平台不允许的「永不中断」，更可靠的目标是「断了能自愈 + 断了能看见 + 一键恢复」。前两项（自愈 + 首页显示上次收到通知时间）已实现，第三项（设置页自检按钮）也已接好。

### 先看现场数据：其实抓到了

用户 21:01 反馈「退出软件后无法自动获取」。真机诊断结果：

| 证据 | 值 |

| 实时监听列表 / 进程 | 都在，`stopped=false suspended=false` |

**结论：后台链路没断，那笔真的抓到了。** 用户之所以觉得「没获取」，是两个产品缺陷：

1. **待确认不参与首页统计** —— 首页「本月总支出」还是 ¥0.00，看起来像没记；

### 本轮实现（用户已明确要求「让 App 一直常驻」）

- 启动点：`MainActivity.onCreate`、`BootReceiver`（开机/升级）、`onTaskRemoved`；
- 设置页开关「后台常驻守护」，**默认开，可关**。

**② 抓到新流水立刻提醒** —— `zhizhang_capture` 渠道，标题「知账抓到一笔 ¥13.14」，点击打开 App 去补全；调试注入带 `[测试]` 前缀。需要 `POST_NOTIFICATIONS` 权限。设置页开关「抓到新流水时提醒」，默认开，可关。

**③ 首页直接显示待确认金额** —— 卡片由「11 笔流水待确认」改成 **`3 笔待确认 · 合计 ¥39.83`**，副标题写明「抓到的流水先放这里，确认后才计入总支出」。

## 二十二、手机重启后呢？有自启动吗？（真机实测）

**有，而且实测通过：重启后无需任何手动操作，自动记账全部恢复。**

### 开机后自动合闸的三层

| 层 | 做了什么 | 谁负责 |
| --- | --- | --- |
| ① 权限层 | 通知使用权登记持久化在 `settings_secure.xml`，开机后系统自动重新绑定 `NotificationListenerService` | Android 系统 |
| ② App 层 | `BootReceiver` 收 `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED` → 刷新小组件 + 启动 `GuardForegroundService` + `ListenerGuard.ensureIfStale()` | 知账 |
| ③ 守护层 | 前台服务 `START_STICKY`，被系统回收后自动重建 | Android 系统 |

**小米「自启动」开关**是厂商私有开关，ADB 查不到也改不了（`dumpsys package` 里没有 autostart 字段），必须在手机管家手动开 —— 用户之前已开启。它是 `BOOT_COMPLETED` 能否送达静态广播的前提。

### 真机实测（21:19 发起 `adb reboot`）

| 检查项 | 重启前 | 重启后 |
| --- | --- | --- |
| 通知使用权登记 | 有 | **有** |
| 实时监听绑定 | 1 | **1** |
| 前台服务 `isForeground=true` | 1 | **1** |
| App 进程 | 1 | **1** |
| 电池优化白名单 | 1 | **1** |
| `ACCESS_RESTRICTED_SETTINGS` | allow | **allow**（重启后被重新刷新） |
| 账本 | 15 笔 | **15 笔保留** |

启动耗时约 30 秒（`sys.boot_completed=1`），手机自动亮屏解锁。**关键验证：重启后不做任何手动操作，直接注入一条支付通知** → 账本 `16 笔 NEW=1`，通知栏弹出「[测试] 知账抓到一笔 ¥16.16」。

截图 `xiaomi-after-reboot.png` 直观显示：常驻通知「知账后台守护中」+ 抓到提醒「¥16.16 · 待确认，点开补全」都在通知栏里。（画面里「打开未成年人模式？」是小米重启后的系统提示，与知账无关。）

### 几个如实说明

- `last_rebind_at` 重启前后没变 → **系统自己重绑了监听服务**，App 的自愈 `requestRebind` 只是兜底，不是主力。这反而是好消息。
- 无法严格区分前台服务是被 `BootReceiver` 拉起、还是 `START_STICKY` 被系统恢复的，但「重启后常驻在跑」这一结果已确认。
- **重启不会重置授权**，但 **HyperOS 大版本更新**有可能重置侧载应用的「受限设置」标记，届时通知使用权开关可能变灰，需要手动勾一次或插线重跑 `fix-xiaomi-notification.bat`。
- 如果重启后手机**停在锁屏没解锁**：`BOOT_COMPLETED` 只在解锁后发出，App 要等解锁才启动（Android Direct Boot 下应用数据不可访问），这是正常现象。
- 用户「强行停止」、管家冻结、卸载依然能停掉它 —— 平台规则不变。

### 你要做的只有这些
